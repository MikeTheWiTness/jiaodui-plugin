# revise 校对工具升级计划（简化落地版）

日期：2026-10-19。状态：**P0 已获用户验收；取消 P0.5 三臂选路实验，直接采用 A：无状态 v3 提案。生产 v3 core、CLI、双插件与 skill 接线已实现；完整 CI 1473 项通过，12 题经新入口 CLI/core 真实验收完成（最终 4 处修订、Word 4 标记=4 锚点、无缺失）。原生插件宿主调用未测，见验证记录。**

本版根据用户“撤销冗余繁复的测试、明确一个落地方案”的要求，替代旧版实验分支计划。选 A 是工程范围决策，不是 A/B 实测胜出的结论。旧实验代码与证据保留历史，不继续推进，也不冒充生产实现。

## 1. 唯一方案

沿用现有校对主链，只简化子 agent 提交修订的方式：


    snapshot → 读单元 / 真实读图 / 按需 calc
             → 提交「原文、改为、原因、证据」
             → core 自动定位并编译 v2 → verify → 父复核
             → 整卷报告 / Word 批注

- 不再要求模型先取 location_id，再重复填写 expected_original。
- 身份、源文摘要、提案版本、总结严重度由 core 绑定或推导。
- 提交仍是一次单元提案；需要返修时，支持按已提交修订 ID 撤回和新增，不重抄全部内容。
- 不增加草稿、工作代次、open/finish、持久工作日志或新的存储布局。
- 物理和化学共用 core；插件仅透传参数，模型负责判断，程序负责定位、校验和生成报告。

选择理由：现有实际痛点在定位重复填写及返修证据残留；P0 已有锚点和证据分层能力，A 可以直接复用，且报告及 proposal 落盘仍是 v2；现有数据文件增加可选 submission_v3 保存当前有效分层提案，便于准确撤回局部图片观察，不保存草稿或修订历史。不为尚无明确需要的崩溃续做引入 B 的状态机。

## 3. 提交接口

### 3.1 完整提案


a) 外层参数仍给 task_id、unit_id 和 expected_snapshot_sha256。
b) proposal 使用 schema_version=3，含 corrections、unit_evidence、self_check。

每条 correction：

- id：单元内唯一 ID；
- old_text、new_text、reason、category、severity；
- evidence_ids：单元证据引用；可附 evidence 数组承载该修订局部证据；
- 可选 context_before、context_after、occurrence：只在重复原文需要消歧时填写。

无问题时 corrections=[]，仍提交核验依据和 no_issue_review 自查。new_text 为空表示删除；不做零宽插入或纯图片替换。

### 3.2 编译与拒绝

- 复用 P0 resolve_anchor，精确定位优先；只沿用已有受限归一化，不新建模糊匹配算法。
- 原文找不到、重复且未消歧、切断公式/加粗、有效修订重叠时，返回明确诊断，让 agent 修正；不得静默选位置或改源文。
- 复用 merge_layers，将有效修订及证据编译成 v2。撤回修订不留下失去引用的局部证据；图片覆盖继续保留。
- 编译结果直接走既有提交事务、图片/calc 证据校验、verify 与父复核。不能旁路闸门。
- summary 按有效修订最高严重度推导，空集为“无问题”；其他绑定字段由 core 填写。

### 3.3 返修

- base_proposal_revision 指定当前同轮、同输入的已提交提案。
- withdrawn=[{id, reason}] 撤回旧修订，corrections 添加新修订；修改一条就是撤回旧 ID 并新增 ID。
- unit_evidence 省略则继承，给出则整体替换；沿用 P0 的继承证据修剪。
- 每次重新提交 self_check；基础版本过期即要求重读当前 snapshot，不自行合并冲突。
- unit-snapshot --with-proposal 只返回当前修订的精简列表，便于引用 ID。

## 4. 实施顺序

| 步骤 | 工作 | 完成判据 |
| --- | --- | --- |
| 1. core | 新增 proposal_v3，校验并编译完整/增量提案；unit-submit 按 v2/v3 分派；snapshot 可返回精简提案 | 合格 v3 能走既有 v2 提交，撤回不留残余证据 |
| 2. CLI / 插件 | 导出 v3 schema，两学科 unit_submit 接 v3；删除模型手填定位/绑定字段的要求 | CLI 与两插件 schema 一致，壳无业务逻辑 |
| 3. skill | 更新两份操作手册及随包副本，入口不膨胀 | 正常流程改为直接交原文修订，明确有限重试和父复核 |
| 4. 真实验收 | 用同一份 12 题 DOCX 经新入口完整跑一次，子 agent 并行最多 6；核对实际读图、修改理由、报告和 Word | 12 题得到明确结果，合格单元通过 verify 与父复核；不能完成的如实留痕 |
| 5. 切换 | 更新正常入口说明，保留显式 v2 兼容入口 | 保持 schema2 与 v2 消费契约，仅扩展可选 submission_v3；不改布局、不迁移历史，能回退旧入口 |

不新增独立 revise-check 工具：先使用既有 unit-submit --preview 做整包预检，定位错误由提交诊断指出。不实现专门的定位拒绝持久计数；沿用宿主有限重试，重复诊断不能解决即停止该单元并报告，不为凑“无问题”丢弃发现。

## 5. 必要验证（收敛后的范围）

### 5.1 核心契约测试

只围绕新增行为写有代表性的正反向测试，不展开笛卡尔积或重复覆盖 P0 已锁定的细节：

1. 合格修订、无问题提案能生成 v2，报告可逐字还原源文。
2. 不能唯一定位、结构切断、重叠会拒绝；错误信息能指导修正。
3. 撤回/替换后旧修订和其局部证据不再渲染，共享证据和图片覆盖不丢。
4. 过期基础版本/当前 snapshot 被拒；既有图片及 calc 证据闸门仍有效，不为 v3 重复铺开全套矩阵。
5. 两插件 v3 schema 与 core 一致，旧 v2 入口保留。

确定性新增逻辑按红→绿实现。开发中跑相关测试；交付前跑一次完整 CI 口径，不再每个小步骤重复跑默认和 CI 两套相同测试：


    .venv/bin/python -m pytest -o addopts='' -q -rs

不删除或跳过已有正确的安全/契约回归测试，不修改预期值凑通过；取消的是本次升级额外堆叠的实验和验收门槛。

### 5.2 真实材料验收

新入口在真实宿主完成一次 12 题流程即可作为本次功能验收依据，无需三臂重复跑 36 次。验收看：

- 使用了新 v3 提交，而非只跑旧入口；子 agent 实际读取材料图片，必要计算实际登记。
- 修改有合理依据，正常错误选项不当作校对错误，纯润色不强改；父复核可退回误判。
- 原文件未改，报告通过 verify，父复核与当前版本一致。
- Word 标记数 = 锚点数 + 公式兜底数，缺失和图片缺失为 0；允许的公式降级如实提示。
- 出现失败时保留原因并修复具体问题；“跑完”不等于无视失败自动通过。

宿主原生插件完成一次可用性冒烟即可；若只能走 CLI/core，明确说明该路径，不强加 token 导出、全工具日志、profile 改造作为 core 功能验收条件。不宣称未测路径已通过，不以小样本证明准确率或性能提升。
