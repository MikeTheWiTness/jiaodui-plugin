## 3. 本次竖切暴露并修复的确定性缺陷

### 3.1 讲义网格表塌成单个超长单元（决定性）

症状：规则拆分只出 1 个单元、65390 字符，预检判超长。
根因：本讲义整篇在 Word 表格里，pandoc 渲染为网格表，`**例1**`/`**例2**` 落在表格行内（行首是竖线）；
而 `section_pattern` 的例题分支是行首锚定 `^\*\*(例|练|变式|真题)\d+\*\*`，失配 → 整篇归入「引言」。
旧仓在导入阶段默认执行 `comprehensive_clean`（去表格竖线、丢表框线、保护公式）与 `strip_decor_images`，
新仓照抄了这两个函数却从未接线。

修复：`split_lecture` / `slice`（讲义模式）默认执行导入清理，新增 `--no-clean` 逃生口；
commit `d0831b8`，回归测试 `tests/test_split.py::TestSplitLecture::test_section_mode_cleans_grid_tables_before_split`。
修复后同一源文件拆出 5 个单元（839–1441 字符），与旧仓全链路复跑结果一致。

### 3.2 讲义公式处于 pandoc 过度转义态

症状：单元源文里所有行内公式都是 `\$...\$`、命令是 `\\mathrm`；不还原则公式进不了 Word 公式、也无法被 `$...$` 识别。
根因：旧仓导入阶段对讲义执行 `fix_latex_escapes`（`\$`→`$`、`\\`→`\`、保护数学块），新仓未移植。
修复：移植为 `jiaodui/convert.py::fix_latex_escapes_text`，接入 `prepare_lecture_content` 的第一步，
顺序固定为 `strip_decor_images(comprehensive_clean(fix_latex_escapes_text(content)))`；旧仓 400 行测试整份移植到 `tests/test_fix_latex_escapes.py`（期望值原样保留）。
修复后单元源文 `\$` 数为 0，行内公式恢复为 `$x$` / `$t=7 \mathrm{s}$`。

### 8.1 拆分导入清理仍缺三块接线（本次修复）

旧仓讲义导入阶段在拆分前固定执行六步；M1 只接线了前三步，漏了后三步中的三块：

| 步骤 | 旧仓实现 | 新仓落点 |
| --- | --- | --- |
| 【出题意图】清理 | `core/defaults.clean_intent_markers` | 本轮移植为 `jiaodui/convert.clean_intent_markers`（含 `DEFAULT_INTENT_PROBLEM_MARKERS` / `get_intent_problem_markers`），旧仓整节测试原样移植 |
| 题图挪位 | `core/defaults.fix_floating_images` | 函数早已移植却从未调用；本轮补文本级 `fix_floating_images_text` 并接线 |
| 选项空格压缩 | `core/defaults.normalize_option_spacing` | 同上，补 `normalize_option_spacing_text` 并接线 |

`prepare_lecture_content` 现按旧仓顺序固定为：
`fix_latex_escapes → comprehensive_clean → clean_intent → fix_floating_images → normalize_option_spacing → strip_decor_images`。
学科独有的题目标志（如 `真题\d+`）由 `split_lecture` 经 `get_intent_problem_markers(config)` 合并后传入；
`slice` 入口没有学科配置，只能用通用标志。

**对 M1 样本的影响**（同一 raw 复跑 split）：仍是 5 个单元，但单元正文变化——
`A. ![test](image5.png) … 选项` 变为独立图片行 + `A.  选项`，选项与解答的长空格压成 2 个。
字符数由 1006/783/1303/784/1160 变为 **1006/655/1175/656/1032**（单元1 无浮图/长空格，不变）。

**闸门后果**：上文 §5–§6 的报告与 docx 是按旧源文校验/生成的。换成修复后的源文，
`verify-report` 逐单元退出码为 **0/4/4/4/4**（单元2–5 因未标记正文差异被判缺段/多段）。

### 8.2 公式渲染失败是环境（matplotlib 无法加载），不是缺代码

- `jiaodui/formula_render.py` 与旧仓 `shared/formula_render.py` 逐逻辑等价（新仓改为惰性 import
  且用 `except Exception` 兜底，是超集），不存在缺失实现。
- 真因：本机 `.venv` 里 pip 装的 `matplotlib` C 扩展被 macOS 代码签名拒绝——
  `dlopen … not valid for use in process: mapping process and mapped file (non-platform) have different Team IDs`。
  DSH 运行时 Python 与 numpy/PIL/lxml 的 `.so` 由 DeepSeek 证书（TeamID `NAN929V4UM`）签名，
  pip wheel 的 `.so` 只是 ad-hoc 签名，加载即失败。
- 后果：`latex_to_png` 返回 False，批注内公式按契约降级为 `$…$` 文本。注意这与验收里的
  「公式兜底」不是同一机制：后者指标记锚点落在公式内时改用正文高亮 + 修改意见；批注公式图片是另一条渲染路径。
- 代码侧修正：`check-env` 原先用 `find_spec` 判定 matplotlib「已安装」，会掩盖装载失败；
  现改为真实 import（`_module_state`，区分「未安装 / 已安装但无法加载」），并新增
  `formula_render.matplotlib_available()` 供 `check-env` 与测试统一判定。原先用 `find_spec`
  判定的 5 个测试因此被误导：4 个 `test_formula_render` 渲染用例失败、1 个 docx 公式图片断言失败；
  改用真实 import 后全部稳定（该 4 例转为 skip）。
- 运行环境要恢复公式渲染，需要 DSH 运行时补一份用其证书签名的 matplotlib；在仓库内无法用 pip 解决
  （任何 pip 装的 C 扩展都会被拒绝）。
