# revise 校对工具升级计划

日期：2026-10-19。状态：设计提案，尚未实现；本文件不代表现有接口已变更。

目标：子 agent 发现一处问题即可用类似 edit 的工具登记「原文 → 建议内容 + 原因」，程序即时定位、校验并持久保存；单元完成时，程序从不可变源文和当前有效修订生成报告，继续走既有校验与父复核。

## 1. 当前实现与改造范围

当前正常链为 `unit_snapshot → unit_read / read_image / calc / unit_locate → unit_submit → unit_review`。子 agent 已经不写报告正文；`unit-submit` 接收 schema v2 提案，core 生成报告、verify、落盘和技术登记，父代理接受当前版本后才算正式完成。

当前摩擦在于定位和修改分离、修改项需要整包重交、证据字段需要搬运，且提交前的提案没有逐条持久化。新方案重点改善这些交互，不重写报告格式。

首版包括严格唯一定位、逐条新增/更新/撤回、证据记录、断点恢复、显式完成、现有交付闸门接入。源文件保持不可变；不生成另一个「修改后源文件」。图片问题仍通过有正文锚点的建议表达；纯图片替换、零宽插入及自动改写 Word 留待单独设计。

## 2. 推荐的子 agent 流程

1. 按派发提供的 task/unit/attempt 身份打开或恢复单元修订工作，取得 `work_id`、源文版本及 `work_revision`。
2. 用现有 `unit_read`、真实读图和 calc 核验。通过工作接口增量记录假设、符号、图片观察和计算引用。
3. 每发现一处问题调用 `revise`，即时获得成功确认和程序分配的修订 ID；参数有误则当场得到候选位置或结构诊断。
4. 通过工作接口读取当前有效修订；有误判时更新或撤回，不重抄整包建议。
5. 显式调用 `unit_finish` 提交自查结论。core 将当前工作记录编译为完整 schema v2 提案，再调用既有提交核心。
6. 子 agent 返回一行摘要。父代理通读汇总报告，对当前 snapshot 调用既有 `unit_review`。

空修订集必须显式 finish，并提供无问题核验依据和 `no_issue_review`。没有修订记录只表示尚未登记问题，不自动表示校对完成。

## 3. 工具面：三个职责

名称为拟定接口，实施前通过 schema 测试固定。CLI 与插件均调用相同 Python core；插件不承担定位、证据回填或状态判断。

| 工具 | 职责 | 关键输入 |
| --- | --- | --- |
| `jiaodui_unit_work` | 打开/恢复工作、分页读取修订、增量登记证据 | `operation=open/read/evidence`；open 使用 task/unit/attempt 身份，后续使用 work_id |
| `jiaodui_revise` | 新增、更新、撤回一条建议 | work_id、action、版本及操作幂等键；修订内容见下文 |
| `jiaodui_unit_finish` | 封存当前有效建议并生成、校验、登记报告 | work_id、版本及操作幂等键、self_check；不再提交 corrections 全量数组 |

open 返回的持久 work_id 关联 task/unit/run/输入摘要/派发 attempt。后续模型不重复填写 hash、位置 ID、建议编号和 proposal_revision。work_id 仅用于查找工作记录，不引入凭证管理。

所有修改工作状态的调用携带 `operation_id` 和 `expected_work_revision`；成功结果返回新 revision。只读 read 不要求幂等键。首次 open 使用身份和 operation_id，重放返回原工作。有效工作上的 open 仅恢复，不隐式清空、复制或创建另一份工作。

### 3.1 revise 示例

假定已通过 evidence 操作获得 `e1`，新增建议如下：

```json
{
  "work_id": "w1",
  "action": "add",
  "operation_id": "op-2",
  "expected_work_revision": 1,
  "old_text": "研究对象为木板",
  "new_text": "研究对象为木块",
  "reason": "题干已将研究对象定义为木块，此处对象名称不一致。",
  "category": "term",
  "severity": "一般问题",
  "evidence_ids": ["e1"]
}
```

`reason`、`severity` 和真实证据引用必填；category 首版保留当前必填语义。修订 ID、精确位置、源文摘要及最终报告编号由程序生成。单元总结严重度由当前有效修订的最高严重度推导，空集为「无问题」。

`update` 要求 revision_id 和完整的新建议内容，原记录保留；`retract` 要求 revision_id 与撤回原因。更新时忽略被替代项自身的区间，再检查与其余有效项的冲突。撤回不删除历史。需要合并多条冲突建议时，先显式撤回旧项再新增，单元尚未 finish 期间不产生新交付。

### 3.2 唯一匹配与结构边界

- 在绑定版本的不可变单元源文中逐字查找，不做 Unicode、空格或 LaTeX 归一化，不做相似匹配；包括相互重叠的文本命中也须计数。
- 一次命中才接受。零次或多次命中均不落盘；返回命中总数、有限候选及分页信息，不静默取第一处，不提供 replace_all。
- 重复短语可增加可选 `context_before` / `context_after`：与 old_text 紧邻、逐字匹配，仅用来确定唯一位置，不写入替换范围。仍多解则拒绝。也可扩大 old_text/new_text 到完整句子。
- 定位完成后复用现有 Unicode 区间和安全结构检查；old_text 切断公式或加粗结构时，返回应覆盖的完整原文并拒绝，不静默扩大用户所提替换。
- 拒绝空 old_text、空操作、空白原因及与有效修订重叠的区间；new_text 允许为空以表达删除。新增内容通过替换包含锚点的非空原文表达。
- 原文含竖线、括号、反斜杠等字符时原样记录，生成报告时复用 ADR 0006 编码。

### 3.3 证据增量登记

`unit_work(operation=evidence)` 支持逐项登记假设/符号/图片观察和计算引用，程序分配证据 ID，read 返回可引用清单。模型必须写内容判断，结构数据尽量由程序取得。

- 图片引用序号由模型选定；原图路径、实际读取路径和位置从当前图片清单回填。模型提供看到的内容及图文一致性判断。登记不等于证明读图，仍须宿主真实冒烟。
- 计算证据引用真实 call_id；core 校验 task/unit/run/源文摘要、成功状态，回填原生结果。多参数调用需要 expression 时，由模型选择账本中存在的参数路径，core 按该路径取原值，禁止拼接表达式或猜选参数。
- 不适用的图片/计算仍须显式说明；finish 时按现有规则检查假设、符号和全部图片引用覆盖。
- evidence 登记时校验单项结构和身份，revise 时校验引用存在；单元级覆盖和自查在 finish 校验。被有效修订引用的证据不得直接删除或更换含义，应新增证据并更新引用。
- 编译后输出现有完整 evidence 结构，继续执行当前 v2 校验。旧 unit-submit 的严格参数校验保留，不把回填逻辑散落到 JS 或 CLI。

## 4. 持久化、版本和恢复

### 4.1 存储位置

工作记录存入材料 `_校对记录.json` 当前轮次下，按 unit_id 组织。记录包含 work_id、工作格式版本、绑定输入、基础交付 snapshot、active attempt、work_revision、状态、操作历史和幂等结果。当前有效修订/证据由操作历史确定性归约得到；如缓存视图，读取时验证一致性。

首版不在 `_校对数据.json` 混放草稿，避免破坏它作为已提交 v2 数据的语义；不新增自由命名的草稿、attempt 或副本文件。新轮保留旧工作历史，但旧 work_id 不能继续写入。长记录的体积和材料锁竞争纳入性能验收，再决定是否另立存储 ADR。

### 4.2 并发、幂等与旧实例隔离

- 每次写入使用既有材料锁、工作区 realpath 检查和原子文件替换；锁内重新核对当前轮次、输入、执行模式和工作版本。
- 相同 operation_id + 相同规范化请求返回原结果，字节及 mtime 不变；即使上次响应丢失也不重复登记。相同 ID 携带不同请求拒绝。
- 幂等重放先核对同一工作、轮次、输入和当前 attempt 的有效性，再查原结果；有效重放可返回原成功结果，不因旧 expected_work_revision 再次失败。
- 不同请求持旧 work_revision 时拒绝，返回当前 revision，调用方先 read 再决定；不能盲目覆盖。
- 绑定当前派发 attempt。技术重派时由父侧显式接管，原 attempt 失效，新 attempt 可恢复同一工作；旧实例的后续写入和 finish 均拒绝。接管入口只暴露给父侧，不能仅通过子 agent 的 open 实现夺取。
- 源文/图片/轮次改变时工作失效；不自动将旧位置、旧计算或旧接受结果移植到新输入。
- 技术重派恢复草稿不重置六类预算；operation_id 与恢复记账 attempt_id 分工明确，不能互相替代。

### 4.3 工作状态与交付状态

工作状态为 `open → preparing → submitted`，输入或轮次变化则为 `stale`；技术取消按既有取消记录处理。finish 在准备提交前校验失败时保持 open 并返回完整错误；进入 preparing 后按下节恢复规则处理。失败留痕沿用 `_校对失败.md` 契约，不抹掉有效修订。

初次打开空工作不算完成；已有交付重新进入校对时，必须显式开启新的工作代次，旧工作保持只读。重校 open 就将该单元标为「本轮未完成」，旧报告保留可查，旧 accepted 不能继续支撑当前交付。开始已接受单元的重校由父侧按现有定向复核流程发起，子侧 open 不能隐式推翻当前已接受工作。

父复核退回后，新工作代次可由程序从当前 v2 提案继承建议和证据，但仅在同轮次、同输入下允许，并记录继承来源；继承不代表通过新的自查或父复核。新输入必须重新核验，不盲目继承。

status、dispatch-plan、build-report、parse-report、build-docx、父复核和本轮完成判定必须共享同一工作有效性判断。存在当前未完成工作时，不将旧报告误当成新工作成果；汇总给出重校占位及原因，旧报告只作明确的历史读取。

## 5. 完成提交与既有 v2 的连接

新增 core 编译适配器：将当前有效修订和证据转为现有 schema v2。位置 ID、expected_original、correction ID、summary、身份、hash、proposal_revision 均由程序计算，保留当前报告格式和下游解析方式。

finish 在材料锁内验证基础交付 snapshot 和工作版本，调用共用的锁内提交实现，避免嵌套加锁。提交事务涵盖报告、数据、技术登记、工作封存及幂等结果；异常回滚到提交前一致状态。进程在各写入步骤被强杀后的恢复也必须有确定结果：完整确认成功或显式拒绝继续交付，不能只依赖 Python 异常回滚。

崩溃恢复采用材料记录内的准备日志：候选校验通过后，先原子登记 preparing、不可变编译提案、预期输出摘要和 operation_id，再写报告/数据，完整 verify 后以最后一次材料记录写入完成登记、submitted 和幂等结果。正常异常可在锁内恢复原文件并撤销准备状态；进程强杀留下 preparing 时，后续写入先在锁内按日志重建相同候选并向前完成，禁止接受另一次提交。若绑定输入、准备日志或当前文件不满足恢复条件，停止并保留现场交父侧处理，不能猜测覆盖。只读 status/下游见 preparing 就报告未完成，不悄悄修复文件。该方案复用现有契约文件，不靠持久临时副本保存恢复状态。

已提交数据增加独立的来源元数据，绑定 work_id、封存 work_revision 和有效工作摘要；不向严格的 proposal 顶层塞入未知字段。父复核及完成判断同时校验该来源；即使重校后报告字节相同，旧 accepted 也不能自动复用。新接受仍只对当前 snapshot 有效。

现有 `unit-submit` 保留完整 v2 兼容入口。单元存在当前 open 工作时，直接提交必须被 core 拒绝，避免旁路绕过草稿；没有工作历史的旧材料按原流程运行。新工作已提交后，后续修订必须显式开启新代次；旧入口如要接管同样先经父侧显式转换，不静默覆盖。

## 6. 错误、预算与诊断

新增错误码必须在 core 中加入确定性预算映射，并覆盖正反测试。建议分组：

| 情况 | 恢复类别 |
| --- | --- |
| 请求字段不合法、工作版本冲突、错误 work/attempt | `call_correction` |
| 原文找不到/不唯一、结构切断、区间重叠、修改内容无效 | `report_repair` |
| 计算引用/参数路径/结果绑定失败 | `calc_representation` |
| 图片证据结构或清单绑定失败 | `image_schema_fix`，沿用连带扣费 |
| 内容被父代理退回 | `targeted_review`，沿用父侧规则 |

源文或轮次改变不能通过重试旧请求恢复；返回停止标志交父侧重建工作。用户取消、权限拒绝及技术重派继续沿用既有处理。

有限候选分页是诊断显示策略，失败记录仍保存完整结构化输出及产物摘要。新恢复不能靠换 operation_id/work_id 重置预算；实施前检查现有失败事件、恢复授权与下一次调用的实际接缝，确保拒绝后不能无限换参数重试。

## 7. 分阶段实施

| 阶段 | 交付 | 阶段验收 |
| --- | --- | --- |
| P0：固定行为契约 | PRD 增量、待采纳 ADR、工具 schema、错误表、独立样本 | 明确唯一匹配、重校状态、幂等、接管和事务恢复；区分提案与已支持行为 |
| P1：纯定位与修订模型 | `jiaodui/revisions.py`（拟定）及失败测试 | 单/零/多匹配、上下文、结构边界、更新撤回与归约结果符合独立预期 |
| P2：持久工作核心 | `jiaodui/unit_work.py`（拟定）、CLI 接口 | 中断后可恢复；并发无丢失；重放不写盘；重派拒绝旧实例；越界写入拒绝 |
| P3：证据和完成提交 | 证据适配器、共用锁内提交、来源元数据与状态接线 | 从工作记录生成 v2；失败不污染交付；旧接受失效；全部下游拒绝未完成工作 |
| P4：插件与 skill | 物理/化学插件、对应 skill 及随包副本、schema/目录测试 | 子侧可 revise/work/finish，父侧接管与 review 隔离；无 shell/write/edit；两学科调用同一核心 |
| P5：真实宿主与切换 | 冻结样本 A/B、真实读图/中断恢复/重派、测试记录 | 正反契约全过；两插件分别真机通过；达到下述门槛才改为正常入口 |

先完成 P1–P3 的 CLI 竖切，再接插件；不同时重构拆分、Word 锚点或学科判断。P0 更新 PRD/ADR，切换时同步 AGENTS 中「unit-submit 为正常入口」的表述，保留其“结构化提交、程序生成、父复核”的硬约束。

主要修改面：`source_index.py`、新增修订/工作模块、`unit_delivery.py`、`report_suggestions.py`、`material.py` 中恢复/完成/派发逻辑、`status.py`、`review.py`、报告与 Word 下游闸门、`cli.py`、两插件 tools/schema、两套 skill 及随包副本。优先抽取共用判定，避免各下游重复写状态分支。

## 8. 验证与切换门槛

确定性功能按红→绿实施，预期位置和报告来自人工固定样本，不用待测定位器生成预期。

- 定位：严格唯一匹配及零/多匹配拒绝；重叠出现的短语、上下文消歧、跨行/CRLF/emoji/零宽字符、完整公式/加粗、特殊标记字符。
- 修订：新增/更新/撤回、重复请求、同键异参、重叠建议、已撤回建议不进报告、严重度随有效集合变化。
- 证据：有图和无图双向；缺图观察拒绝；跨单元/旧轮/失败 calc 拒绝；多参数路径合法则接受；不得生成伪造证据。
- 状态：空草稿不完成；旧 accepted + 新工作不完成；新工作提交相同报告仍需新接受；needs_revision 后可重新派发并继承有效提案。
- 恢复：两个 CLI 进程竞争同一版本、多个单元并发、响应丢失重放、子进程强杀、接管后的迟到写入、换轮/换输入失效；所有写入点注入失败并检查可恢复一致性。
- 闸门：finish 生成合格 v2 必接受；位置/证据/自查/图片/来源无效必拒绝；直接 unit-submit 不能绕过 open 工作；旧 v2 及逐份标注的历史报告仍按原预期。
- 交付：源文和源图 hash 不变；报告逐字可还原；Word 标记数 = 批注锚点数 + 公式兜底数，缺失 0；父代理仍只收单元摘要并最终通读汇总报告。

执行定向测试后运行仓库全量与 CI 口径：

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m pytest -o addopts='' -q -rs
```

冻结 A/B 至少包含：无问题、文字错误、重复短语、公式修订、带图、同位置误判撤回、父复核退回、技术中断恢复。固定输入与学科规范，分别记录当前 unit-submit 链和新链的工具调用数、参数/定位/提交拒绝数、输出 token、耗时、报告一致性与人工判定的误报/漏报。

切换硬门槛：上述确定性正反测试全部通过；新增真实读图与中断恢复验证；两学科均有合格接受与不合格拒绝；未出现旧报告冒充新完成。易用性目标：减少模型搬运字段和参数/定位类失败，内容质量不下降；逐条调用可能增加往返，必须同时报告总耗时和 token，不预先宣称更快或更便宜。小样本只能证明流程可用，不能宣称已证明质量统计提升。

P5 通过后将 revise/work/finish 设为 skill 正常入口，旧 unit-submit 留作显式兼容。尚有 open 工作的材料暂停自动切回旧链；应先由父侧显式处理工作状态并保留审计，避免绕过本轮未完成状态。数据库式迁移和另一个报告 schema 均非本次前置条件。
