0. 这份文档怎么用

给未来的执行者（尤其是新开窗口的 agent）：

  • 先读图，再读决策表。本文档的 11 张图是 Mermaid 源码，既可渲染也可纯文本阅读；文字段落是对图的注解，不是唯一信息载体。
  • 决策有编号（D1–D30）。每条决策都写了「理由」与「被否方案」。执行时若想改某条决策，请先看它的被否方案为什么被否 —— 多数看似更省事的做法已经试过或算过账。
  • 「待验证前提」（PV1–PV5）不是结论。它们是把决策建立在假设上的地方，执行到对应环节时必须实测复核；若前提被推翻，对应决策要翻转（文档里标了翻转哪条）。
  • 契约章（§5）是硬约束：产物格式、状态定义、命令接口。流程章（§6）可以按实测调整，契约章不行 —— 因为下游的 docx 生成、整卷报告、旧产物兼容都挂在它上面。
  • 数字来自旧仓真实语料（output/ 的报告与对话记录）；严重度统计已有口径冲突，须按附录 A 复核后才能用于验收。

1. 目标与最高原则

最高原则 Q1：校对质量最高优先。任何与质量冲突的成本、速度、简洁性取舍，一律让位。不设 token 上限，不为省钱少验算、少读规范。

1.1 要达成的目标

  1. 判断交给 agent，确定性交给 Python。删除自研 agent 循环（core/api_client.py 约 1900 行），五个 LLM 环节（智能拆分 / 语文古籍前置检索 / 主校对 / 批注评审 / 格式修正）全部由宿主 agent 完成。
  2. 跨 agent 可分发。同一个 skill 应能在 DSH、codex、kimi code 等不同 agent 里跑；Python 侧零凭证（不持有任何 API key）。
  3. 单元之间零污染。一个校对单元 = 一个独立子 agent 上下文；不再让 20 轮混杂历史影响判断。
  4. 沿用产物文件名，收紧新报告契约。_校对报告.md、_校对数据.json 等旧产物仍可读取和转换；新产生的报告须通过更严格的完整性校验才能进入交付。

1.2 为什么值得做（不是为省钱）

实测输出侧只占全部 token 的 11.4%，消耗全在输入的重复发送上；而 prompt 缓存已把输入成本吃掉 81.5%。所以这次重构买的是：

  • 可维护性：056/057/058 三个 issue 全是在补自研循环的窟窿（压缩是全丢、截断不可见、工具返回不投影）。不重构，这个补丁节奏不会停。
  • 可分发性：现在只有 GUI 一个入口，别人要用只能复制整个仓库 + 配 key。
  • 判断质量：长循环里模型的注意力被噪声稀释 —— 单元 6 的「幽灵标记」就是在 20 轮混杂上下文里产生的。

2. 背景与实测基线

2.1 现状的三个结构性问题

问题具体表现
自研 agent 循环工具循环、历史压缩、断点续传、重试熔断、stop_reason、token 统计全在自家代码里重写一遍。压缩是「全丢」而非摘要，触发条件与 token 用量脱钩；finish_reason=length 长期无语义（057 才补）。
输入侧无预算、无埋点全库搜不到任何「上下文窗口」概念；单次请求的真实 prompt token 从未记录；超窗口只能等 provider 报 400 后靠一句提示文案。

3. 架构总览

三层的分工与纪律：

  • 核心逻辑只有一份，三个壳都不含逻辑（只做参数解析、格式化输出、协议转换）。这是「不重写」的保证：换壳不改核心。
  • CLI 是退路：任何 agent 只要有 bash 就能干活；插件坏了、MCP 挂了，命令行仍然可用。
  • MCP 是通用件：DSH 挂上后工具自动注册为原生类型化工具，codex / kimi / claude 也都认这个协议。
  • DSH 插件包是薄适配：注册原生工具、挂载 skill 目录、定义一个 jiaodui agent preset，可选加客户端面板。

拓扑的三条纪律：

  1. 禁止嵌套。只依赖「支持子 agent」这一个门槛，不依赖「支持嵌套子 agent」；同时让「独立解题」之类需要干净上下文的角色永远由主 agent 发起，可审计。
  2. 子 agent 只拿路径，不拿内容。主 agent 不把源文读进自己上下文（否则就违反「纯调度」）。
  3. 子 agent 不决定自己做完没有。是否完成由确定性的 verify-report 判定（见 §5.2）。

4. 决策清单（30 条）

每条决策都写「理由」与「被否方案」。被否方案是这份文档里最值钱的部分 —— 它记录了哪些看似更省事的路已经试过或算过账，执行时想改决策前请先读它。

4.1 形态与边界（D1–D6）

编号决策理由被否方案
D1交付形态 = agent 驱动，产出一个通用 skill，目标在 DSH / codex / kimi code 等不同 agent 里都能跑判断必须由 agent 做才能跨 agent；Python 只留确定性计算把编排包成一个 CLI 命令（8 月那版）—— 失败原因就是「只是包了一层命令，agent 没真干活」
D2基座 = 新仓重写；JiaoDuiSkill（8 月版）归档为失败样本8 月版缺失 054–058 全部质量修复（audit_markers、MARKER_AUDIT_WINDOW、LENGTH、shrink_tool_result 一个都没有），且方向被判为「形态不对」以 JiaoDuiSkill 为基座、把 054–058 反向移植过去
D3旧仓 JiaoDuiAgent 完全冻结，定位为只读参考；任何旧 GUI 问题都不在旧仓修复制代码必然分叉。上一版整份复制后 7 周，一边有 054–058、一边一个都没有。只要「冻结」不彻底就会长出第二个真源有限维护只修致命 bug（会重新分叉）；新项目反哺旧仓（两套编排长期双轨）
D4五个 LLM 环节全交 agent：智能拆分 / 语文古籍前置检索 / 主校对 / 批注评审 / 格式修正只要留一个环节由 Python 调模型，api_client 就得留着，自研循环、提示词双源、补丁节奏都还在只交主校对，其余保留 Python 调模型
D5强制子 agent：一个校对单元 = 一个干净上下文；不支持子 agent 的 agent 就不支持单元间零污染是本次质量收益的核心；把手段写死换取一致性把「单元 = 上下文边界」只当约束、由宿主自选手段（可分发范围更大，但一致性依赖宿主）
D6一层扁平：主 agent 统调单元校对 / 审计 / 拆分升级三类；禁止嵌套只依赖「支持子 agent」一个门槛，不依赖「支持嵌套」；需要干净上下文的角色（独立解题类）永远由主 agent 发起，输入可审计允许嵌套（单元子 agent 自己开解题子 agent）—— 依赖两级嵌套，且独立解题的输入不可审计

4.2 职责与调度（D7–D12）

编号决策理由被否方案
D7主 agent 纯调度，每个单元只读一行摘要（单元号 / 问题数 / 校验结果 / 产物路径 / 失败原因）主上下文恒定，批量规模只受并发与时间限制，不受上下文限制主 agent 读各单元报告做汇总（主上下文随单元数线性增长，344 份规模必爆）
D8整卷报告由 Python 确定性拼接；主 agent 在全部结束后通读全文现状整卷报告本来就是机械拼装（ui/default_app.py 里按 ## 第N题 串联，无 LLM）；主 agent 1M 上下文读 50 单元大讲义（≈12 万 token）只占 12%大讲义只读「交叉信号」不读全文（在 1M 口径下没有必要）；主 agent 用摘要拼整卷（丢失整体把关）
D9容量口径：主 agent 1M，子 agent 100k与宿主配置一致（profile 里 deepseek-v4.1-flash contextWindow 1,000,000）；100k 对单单元校对「紧但够」：实测最重单元末轮 ≈6 万 token，工具返回投影后 ≈4 万给子 agent 也放开到 1M（失去单元级预算约束的意义）
D10派发 = 滑动窗口补位，并发取宿主上限（DSH 8，可调到 10 与现状对齐）墙钟 ∝ N/并发；单元目录彼此隔离、写入无竞争；主 agent 同时在飞的返回值 ≤ 并发数一次性全派（池会排队，主 agent 看不到进度，返回值可能成批涌回）；严格串行（白丢 8 倍墙钟，质量不升）
D11失败分级：verify 不过 → 自修 ≤3 轮；仍不过 → 标失败、留产物与原因、不阻塞批次；技术性崩溃/超时/限流 → 自动重派 1 次52 个单元里坏 2 个不该让另外 50 个白跑；失败必须留痕可见（057 的教训：截断/失败不能静默）失败即停下询问（一个坏单元拖住整批）；无限重试直到通过（烧钱且掩盖真实质量问题）
D12独立解题冻结，不进 v1；按一次校对的准确性再决定是否启用模型智力比半年前显著提升；先用真实质量数据判断是否还需要这个杠杆所有带答案/详解的题都做一次独立解题并比对（成本约 ×2.5，收益未验证）；维持「难题才做」（自己判定跳过 = 给自己开后门，最不可靠）

4.3 工具与契约（D13–D21）

编号决策理由被否方案
D13工具面只留两族：calc（符号计算 11 个合并，保留符号白名单与浮点容差修正）+ classics（古籍检索 + 确定性 diff）；通用工具（read / write / grep / web / plan / 文本导航）全交 agent 自带通用工具与 agent 自带能力重复；而符号白名单修的是一类真实误判（I 被当虚数单位、S 被当 sympy 注册器、alpha/beta 被当常数），古籍检索是文言文校对的权威性来源通用工具也保留为命令（重复且每步多一次往返）；连古籍检索也交给 agent 自带联网（文言文参考权威性下降）
D14视觉能力是硬前提：主 agent 在任何校对派发前验证子 agent 能读取本地图片；无法确认时拒绝本次执行「图片内容」是通用检查的强制项；Python 的 check-env 只能检查本地依赖，不能证明宿主子 agent 的视觉能力给路径但允许无视觉时降级（跳过图片检查并在产物里标注）—— 少一类强制检查
D15产物文件名沿用 + 新报告交付即校验：子 agent 写完 _校对报告.md 后调 verify-report，不通过不算完成；格式修正并入交付回环保留旧产物的读取能力与下游路径约定；新报告补上源文完整性等检查，不能把历史格式缺陷当作新契约。写文件的行为在各宿主仍需实测子 agent 返回结构化标记数组由主 agent 落盘（依赖返回值可靠性、历史产物不再可比）；纯事后校验（错误发现晚，要回头重派子 agent）
D16状态归磁盘产物，提供 status 命令；完成 = 报告存在且按新契约校验通过，失败记录不能覆盖已修复的完成状态会话不是状态载体：会话丢了也能从磁盘恢复全量进度；现状「文件存在即跳过」会把半成品当成完成状态归主 agent 会话（多一份状态源，会话中断要重扫）；保留轮级续传快照（新架构里子 agent 的会话由宿主管，快照没地方挂）
D17子 agent 输入包 = 路径（源文 md / images / 学科 references）+ 交付要求 + 禁止项（不改源文、不自由命名产物、不嵌套派子 agent）内容内联会要求主 agent 先把每个单元的原文读进自己上下文，直接违反 D7把源文与图片内联进 prompt
D18审计触发 = 交付不符合要求时（verify 不过 / 摘要异常）；由审计子 agent 独立复核指定单元，产出裁定（可修 / 需人工 / 建议弃用）审计的价值在抽查与矛盾发现；全文复读的成本与收益不成比例；格式与标记真实性问题已由 verify-report 兜住，审计应专注判断类漏检每单元必审（成本翻倍且与闸门职责重复）；不设审计角色（失败单元无人复核）
D19Python 侧零凭证：新项目不含 .env、不含 key 管理、不含 env_config判断全在 agent 侧后，Python 只做确定性计算，没有任何理由持有 key；零凭证消除了分发时最容易配错也最容易泄密的环节保留 .env 与凭证管理（多一套配置与文档负担）；只从环境变量读（多一条隐式输入路径）
D20三个壳的顺序：CLI → MCP → DSH 插件核心尚未验证前不引入新依赖（Python MCP SDK）；而 CLI 天然是 MCP 与插件的退路 —— 插件坏了、MCP 挂了，bash 一条命令还能干活MCP 先行（协议调试会拖后「拿到关键数字」这件事）；插件先行（绑定 DSH，跨 agent 与核心逻辑的验证都推到后面）
D21命令 = jiaodui + 命令族子命令：calc / classics 带子命令，其余动作扁平；共 14 个命令，v1 必需 11 个，含规则拆分 splitcalc / classics 内部共享沙箱与 schema；显式 split 是从转换结果进入单元目录的必经步骤全部扁平（calc-evaluate 等十几个顶层命令，名字空间持续膨胀）；单入口 + 动作参数（可读性差、参数更易写错）

4.4 skill 与学科（D22–D25）

5.2 交付即校验（格式修正在此塌缩）

verify-report 是模型产出与下游产物之间唯一的闸门。它检查：

检查项判定
标记语法必须匹配 【编号|原文|改为】；字段缺失、括号不配对 → 拒绝。公式等源文自身跨行时允许跨行字段，解析与 Word 生成须共用同一标记语法
修改原因对应编号必须与 ### 标记原文 中的标记一一对应（多、少、错位 → 拒绝）
严重度总结行必须是四个合法值之一：无问题 / 轻微问题 / 一般问题 / 严重错误；缺失或写成裸「无」等 → 拒绝；「无问题」不得同时含错误标记
原文完整性去掉报告中的标记语法、还原各标记原文字段后，与单元源文逐段比对；缺段、重段、改变未标记正文 → 拒绝。只允许预先列明的换行、空白与转换器装饰差异；仅落在 LaTeX 标记字段里的无法判定差异保留 unknown 警告。不能靠每条标记的局部定位代替全文比对
空原文字段拒绝（旧产物里实测 9 份 / 3.6%）
空操作（原文 == 改为）拒绝（旧产物里实测 8 份 / 3.2%）
原文字段能否在源文定位unknown 不算失败，只记录；理由是实测 86 份可定位产物里有 82 条 unknown，若当失败则历史产物 100% 不合格 —— LaTeX 装饰差异会让合法标记也定位不到
改为与原文字段无法区分标记为「需人工确认」，不拒绝（文本上无法与合法标记区分，宁可多保留一条批注也不静默丢真实发现）

新旧契约边界：新产生的报告必须通过上述严格校验才能视为完成。历史报告仍可读取和转换，但不得仅凭文件存在或旧解析成功冒充新流程的“已完成”；旧样本用于兼容测试时应单独标注其已知格式缺陷。verify-report 对未知定位给出警告，对可确定的源文缺漏给出失败，两者不能混为一类。

5.3 状态与断点

状态只由磁盘产物推导，不依赖任何会话内存。主 agent 通过 status 读取，会话丢失后重新扫一遍即可恢复全量进度。

状态优先级：先校验现有报告；通过则为“已完成”，即使保留旧的 _校对失败.md 也不回退。未通过且有失败记录才为“失败”；未通过且无失败记录为“已交付未过校验”。build-report、parse-report、build-docx 必须复核当前状态，拒绝消费未通过的报告。

命令作用v1

6. 流程

本章描述「一次完整校对实际怎么跑」。所有判断环节都在 agent 侧，所有验证与产物生成都在 CLI 侧。

6.1 单元校对（单元子 agent 视角）

关键点：子 agent 的输入包里没有源文内容，只有路径。这保证主 agent 不需要先把原文读进自己的上下文（D7 / D17）。同时子 agent 被明确禁止：改源文、自由命名产物、嵌套派子 agent。

6.2 批量调度（主 agent 视角）

读图是前置硬门槛。check-env 只能提示，不能代替主 agent 验证宿主能力。主 agent 须在任何校对派发前用实际本地图片验证子 agent 可读取；验证失败就拒绝本次执行，不能静默跳过图片检查（D14）。

6.3 失败路径

情形处理理由
verify 不通过自修 ≤3 轮多数失败是格式与编号问题，子 agent 手上有结构化原因与位置，自修成本远低于重派
自修 3 轮仍不过标失败 + 留产物 + 不阻塞批次52 个单元里坏 2 个不该让另外 50 个白跑
技术性崩溃 / 超时 / 限流自动重派 1 次（仅一次）这类失败与产物质量无关，重派一次便宜且有效；不设无限重试以免掩盖真实问题
失败单元的处理批次结束后交审计子 agent 复核 → 人裁定失败清单必须可见；且「自修到通过」不能变成「用改产物去迎合闸门」（057 的教训）

6.4 收尾

验收硬门槛之一就在这一步：错误标记数 = 错误标记批注锚点数 + 公式可见兜底数，且缺失数为 0；无问题单元的标题批注单列。必须检查生成后的 docx，而非只看生成前计划注入的数量；不满足时不交付 docx。

7. 学科差异的载体

学科之间真正不同的只有三样：检查重点（人读）、工具集与输入格式（机器读）、拆分参数（机器读）。共性流程只写一次，放在总 SKILL.md。

为什么不用「每学科一个 skill」：上一版就有 8 个 skill，改一次流程要动七处，最终各学科提示词漂移成了七八个近似而不同的版本。学科差异必须收敛成表里的行，而不是目录树里的分叉。

8. 质量评估方案

在 M2 开始前冻结一份 22 单元样本清单：逐项记录源文件路径与哈希、学科/来源模式、是否含图片与公式、旧报告路径，以及选入理由。覆盖有标记/无标记、公式内标记、图片题、长单元与旧流程曾漏检的题型；不能在看到新版结果后换样本。两遍使用同一源文，但分别在全新输出目录与子 agent 会话运行，并记录宿主、模型版本、运行时间及可取得的 prompt/completion token；价格字段不可得时标为“未提供”，不得估算成 0。

核心设计：同一批 22 个单元跑两遍，看的是稳定性，不只通过率。

跑两遍的意义在于暴露遵守率是否可靠：如果一遍 95% 通过、另一遍 60% 通过，说明产出的稳定性依赖运气，此时该做的是把 references 的规则写得更死、更可执行，而不是去调流程。单遍低通过率只能说明「要改」，两遍差异大才说明「改的方向在哪」。

序号指标口径与判定
1首次 verify-report 通过率（两遍对比）子 agent 第一次写完报告就通过的单元数 / 22。每遍至少 20/22（≥90%）；两遍通过数相差 4 个及以上（>15 个百分点）即触发 references 回炉
2错误标记到 Word 的覆盖逐单元记录错误标记数、实际批注锚点数、公式可见兜底数、缺失数与无问题标题批注数；必须 错误标记数 = 锚点数 + 公式兜底数 且缺失数为 0。抽查兜底文字中的修改建议可读
322 单元全量人工抽检不抽样。逐单元核对：有没有漏检（该标的没标）、有没有误标（标了但不该标）、严重度判定是否合理
4与旧产物逐单元对照「旧有新版无」只查单向丢失：旧流程发现过而新流程没发现的问题。反向（新版多发现）通常是好事，但也要抽看是否有误标

为什么用「下限对照」而不是「F1 对齐」：旧产物本身不是金标准 —— 364 份报告里只有 68% 带标记、78% 有合规的严重度行、还有 3.6% 空原文与 3.2% 空操作这类不合格产物。把它当绝对基准，等于把旧流程的漏检和错误当成目标。合理口径是：新流程的漏检不得多于旧流程，超过的部分必须逐个解释。

人工裁定口径：两遍结果逐条记录“旧有新版无”“新版有旧版无”及其证据，区分漏检、误标和旧报告本身错误；有争议的样本由第二名复核者裁定，保留裁定记录。任一遍出现尚未处理的严重内容错误漏检，不通过 M2；其余差异须有逐项解释和处理结论，不能用总通过率抵消。

层次方法说明
确定性层（红→绿）移植旧仓测试作行为契约，新功能先写失败测试解析、校验、切片、批注锚点注入、报告拼接 —— 这些有稳定接缝，适合红→绿→重构。接缝越少越好
闸门双向契约真实语料双向测试：不合格必被拒 + 合格必被接受用旧报告做兼容语料，但先逐份标注预期结果与原因：空原文、空操作、漏段等应拒；人工确认满足新契约的样本应接受；unknown 定位只告警。不能把“其余旧产物”未经核对全标为合格
agent 编排宿主适配冒烟测试 + §8 人评CI 用模拟派发/返回覆盖窗口补位、失败重派、断点扫描和防重复派发；在每个宣称支持的宿主上，用真实子 agent 验证路径读取、读图、落盘与摘要回传。判断质量仍按 §8 人评

为什么强调双向：056 的标记审计就是栽在只测「合格样本」上 —— LaTeX 装饰差异会让合法标记定位不到，如果当时把「定位失败」直接当不合格，会被误判为 100% 不合格；而如果为了通过率把闸门放宽到什么都不拒，闸门就失去了意义。两个方向都要有真实语料钉住。

附录 B：术语表

术语含义
校对单元一次独立校对任务的最小单位（试卷的第 N 题、讲义的一个单元），对应一个磁盘目录与一个子 agent 上下文
主 agent流程调度者：拆题、派发单元、收一行摘要、读整卷报告、发起审计。不读单元原文
单元子 agent校对单个单元的独立上下文；只拿路径与要求，产出 _校对报告.md
审计子 agent对失败 / 异常单元做独立复核并给裁定的角色，只在需要时发起
标记报告里的 【编号|原文|改为】 结构，表示「这里错了，应改成什么」
标记审计audit_markers：判断标记的「原文」字段能否在源文中定位，产出 MARKER_OK / NOOP / EMPTY_ORIG / RESTORE_NEW / UNKNOWN
交付即校验子 agent 写完报告后必须调用 verify-report 并使其通过，否则不算完成；格式修正在这个回环里完成
整卷报告按 ## 第N题 串联各单元报告的汇总文件，由 Python 确定性拼接，无 LLM 参与
工具返回投影058 引入的机制：写入模型上下文前的工具返回只保留对判断有用的部分（如去掉代码回显、折叠 traceback），原始内容仍完整落盘
references 渐进披露把学科细节放进 references/ 由 agent 按需读取，保持 SKILL.md 短小（D22）
拆分升级默认规则拆分不可靠时，派子 agent 产出边界清单，再由 Python 按清单切片（D24）
硬门槛M1 / M2 必须达到的验收指标（错误标记无静默丢失、每遍首次通过 ≥20/22、不合格报告不进入交付、模型用量可观测）
